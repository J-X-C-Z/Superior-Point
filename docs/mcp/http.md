# Remote Streamable HTTP MCP

The service exposes `/mcp` using the installed official MCP SDK Streamable HTTP transport. Connect an SDK-compatible client to the configured public origin plus `/mcp`, with `Authorization: Bearer <PAT>` on every request. Keep tokens out of URLs and client logs. This endpoint accepts no cookies, mixed cookie/bearer authentication, alternate Host, or foreign Origin. A missing Origin is permitted for authenticated native clients; a supplied Origin must exactly match the configured service origin.

The transport is stateless and returns JSON. Initialization never issues `MCP-Session-Id`; supplying a session ID returns 400. GET and DELETE authenticate then return 405; there is no SSE notification stream or resumable session. Every HTTP request authenticates again. Every tool business operation passes through the same validated API and ProjectService/ThemeService used by the browser and stdio Bridge, including revocation, active-user, project allowlist, scope, lease and revision-CAS checks. Tool listing describes capabilities and does not grant authority to execute them.

The same twenty cloud tools are registered from `mcp/cloud-tools.js` for HTTP and stdio: `sp_create_project`, `sp_open_project`, `sp_get_document`, `sp_get_slide`, `sp_edit`, `sp_render_slide`, `sp_validate`, `sp_save_export`, `sp_list_projects`, `sp_project_info`, `sp_list_slides`, `sp_list_themes`, `sp_get_theme`, `sp_preview_theme`, `sp_preview_theme_application`, `sp_validate_theme_compatibility`, `sp_apply_theme`, `sp_save_theme`, `sp_list_revisions`, `sp_get_revision`, `sp_revision_diff`, `sp_restore_revision`.

HTTP has no authorized client filesystem. `sp_open_project` accepts `projectId`; the `filename` import variant and `sp_save_export` return `ROOT_REQUIRED`. Use stdio Bridge with an explicit `SP_BRIDGE_ROOT` for bounded local import/export, or the authenticated HTTP export API to receive HTML in memory. Remote filenames are never resolved on the service host. Static slide SVG previews retain the existing renderer compatibility limits.

Request theme scopes explicitly: existing/default PATs do not automatically acquire them. Read-only themes require `themes:read`; saving requires `themes:write`; publishing requires `themes:publish`; applying requires the service's existing project/theme scopes. Keep a stable `clientMutationId` and identical payload when retrying a write whose outcome is unknown. Stateless transport does not retain Bridge's process-local pending mutation cache across requests; server receipts remain authoritative.

`AppOptions.authenticateMcp` is the bearer-validation adapter for additional token providers. It must return a verified MCP Actor compatible with the existing transactional token checks; accepting a JWT-shaped string without issuer, audience, scope, revocation and active-user checks is insufficient. The PAT implementation is the default. Provider tokens are accepted only by `/mcp` and a private nonce bound to a single in-process API dispatch; the public REST API remains PAT-only. The nonce is removed in `finally` and every dispatch revalidates the original bearer. OAuth discovery/authorization belongs to SP-077, independently of the transport.

Verification: `tests/service/mcp-http.test.ts` uses an actual SDK StreamableHTTP client and disposable PostgreSQL schema. Coverage includes initialize/list/create/read/edit, identical mutation replay, revision conflict, themes, cross-user/project isolation, scope denial, revoked-token HTTP denial, Host/Origin, mixed credentials, session-ID rejection and filesystem refusal. This is SDK client compatibility evidence; desktop client product-specific acceptance and public ingress deployment remain separate.

Protocol source: [MCP Streamable HTTP specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

The four history tools reuse the existing revision API. Listing, reading and diff require `projects:read`; restore requires `projects:write`, the project allowlist and an explicit stable `clientMutationId`. Restore first resolves an existing identical receipt; a new restore acquires an exclusive lease and cannot displace an active browser lease. It produces a new revision, retains every historical snapshot, and checks `expectedRevision`. Retry an uncertain restore with the same mutation ID and original expected revision. Structured diffs report changed slide/object IDs plus theme/assets flags; they do not imply a pixel-perfect preview or allow separate asset uploads. Cloud asset library/read-write tools remain unsupported pending the actual asset service.
