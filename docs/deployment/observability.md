# Agent analytics and scoped resource monitoring

SP-079 stores MCP tool-call metadata in `mcp_tool_metrics` (migration 008). The twenty shared cloud tools are the only accepted names. Persisted fields are verified actor ID, tool, duration, outcome, an uppercase diagnostic code, transport and server timestamp. Arguments, document bodies, token values, environment, IP addresses and SQL text are never accepted or returned. Invalid diagnostic strings become null. `MetricsService.recordToolCall` returns false on storage failure and never throws; callers must not retry a document write because its metric was unavailable.

Instrumentation calls `recordToolCall({actor,tool,durationMs,outcome,errorCode,transport})` after the business operation, including authorized actors whose tool call fails. `actor` must come from the verified request validator; do not construct one from user-supplied JSON. The persisted transport enum supports `streamable-http` and `stdio-bridge`. Current integration records native HTTP MCP tool execution; stdio Bridge has not yet received a dedicated tool-duration integration and its complete tool statistics remain pending. Do not infer Bridge tool duration from a single REST request. Unauthenticated requests cannot be assigned a verified actor and do not create an event. Tool metadata alone does not prove a particular document change; document revision receipts remain authoritative.

Read-only admin endpoints are `/api/v1/admin/observability/tools` and `/resources`. They recheck the active admin role and unrevoked web session, without demanding password reauthentication for reads. MCP tokens cannot access them. Tool filters accept ISO `from`/`to` (exclusive upper bound, default last 24 hours, maximum 366 days), `userId`, exact `tool`, `limit` 1–100 and `offset`. Counts and error rate summarize the complete filtered range; rows are paginated by the database rather than filtering a browser page.

`mountObservability({container,api})` renders those endpoints and returns `{refresh,destroy}`. It refreshes every 30 seconds and cancels its timer and delayed render on destroy. Selected time bounds remain fixed during refresh. The admin shell must destroy it when changing sections. Empty records and unavailable resources are shown directly, without sample production data.

SP-080 reports the actual application process CPU counter and interval single-core percentage (which can exceed 100% on multicore workloads), RSS/heap, uptime, application filesystem capacity, counters from the visible Linux cgroup v2 mount when readable, current database connection counts and the duration of the database probe. “Current API request responded” describes this endpoint only. Database output excludes SQL, database names and connection identities. Filesystem figures describe the filesystem mounted at the application's working directory; they are not automatically Hakari whole-host capacity.

Whole-host CPU/memory/disk are **unavailable until independently collected on Hakari**. Pass an explicit `hostMetricsFile` to `MetricsService`; no environment inspection, shell invocation or Docker socket is required by the application. The optional `deploy/hakari/collect-metrics.py` reads Linux `/proc/stat`, `/proc/meminfo` and root `statvfs`, then atomically writes a small numeric JSON file. Run it as an unprivileged host user with read access to those counters and write access only to the dedicated output directory. It does not need root, Docker membership or container inspection rights. An external scheduler should update the file at least once per minute.

Mount the **directory** containing that JSON read-only into the application container, so atomic replacement remains visible. Do not mount a writable host directory, `/proc` from the host, Docker socket or sensitive directories into the app. Configure the application path to the JSON under this mount. Files older than 120 seconds, more than five seconds in the future, malformed, over 64 KiB, symlinked, or containing invalid numeric ranges return unavailable. Only whitelisted counters are returned. Missing collector data never falls back to guessing host statistics from container-visible OS memory.

Container lifecycle is available only when the optional fixed-container host collection is explicitly enabled. cgroup CPU/memory describe the visible cgroup mount: with a private container cgroup mount these are container counters; on another host configuration the mount can encompass other processes. The service does not label these counters as whole-host or process-only usage. The application reads only the sanitized lifecycle JSON, never the Docker daemon.

Local tests verify persistence, filter/pagination, privacy, current admin checks, metric-write failure isolation, host sanitization/staleness, resource probes, UI pagination and lifecycle. No Hakari collector, production timer, mount, alert destination or public ingress has been installed by this change. Actual Linux/Hakari host collection and operational alerts retain separate pending acceptance.

Telemetry is best-effort: tool responses never await persistence. Each MetricsService admits at most two concurrent writes, with a 100ms PostgreSQL lock timeout and 250ms statement timeout. Congestion or unavailable storage can discard events; displayed counts describe recorded events, not a complete billing/audit ledger. Actual exclusive-table-lock tests verify business writes continue and metric storage recovers after unlocking. Configure `SP_HOST_METRICS_FILE` for an explicitly mounted collector JSON path.

## Optional fixed-container lifecycle collection

`collect-metrics.py <output-file> --containers` additionally inspects exactly `superior-point-app-1`, `superior-point-db-1` and `superior-point-caddy-1`. It uses the fixed `/usr/bin/docker` executable and local daemon socket, `--type=container`, and a fixed Go format selecting only `.State.Status`, `.State.Health.Status` (or `none`), `.RestartCount` and `.State.OOMKilled`. It never requests full inspection JSON, Config/Env, Args, networking/IP, labels, logs or other containers. Each call has a five-second timeout; absent/denied containers return a generic unavailable row, without forwarding Docker stderr. [Docker's inspect format documentation](https://docs.docker.com/reference/cli/docker/inspect/) describes the templating mechanism.

Enabling this mode needs host Docker-daemon access. The smallest operator setup is a root-owned, non-user-writable collector script invoked by a reviewed root cron/systemd entry with fixed output path and `--containers`; do not add the application or the unprivileged CPU/memory collector user to the Docker group. Docker-daemon access is privileged even when this specific collector invokes only inspection. The privileged host job writes only sanitized JSON into the same dedicated metrics directory; the application still receives a read-only directory mount and no Docker socket or host execution rights. Without this explicitly configured host job, container status remains unavailable. No privileged job is installed by this change.

The container payload has its own `generatedAt` and `source:hakari-fixed-docker-inspect`, plus exactly three fixed-name rows. State and health are bounded enums; restart count must be a nonnegative safe integer; OOM must be boolean. The application rejects unknown names, duplicate/missing rows, unknown row fields, invalid values and stale/future timestamps. An individually absent container produces `partial` with a generic unavailable row while valid fixed rows remain visible. CPU/memory/disk can remain valid when container data is unavailable. The UI labels these rows as Hakari fixed Docker inspection and displays their independent collection time, state, health, restarts and OOM. This is not a list of every host container.

Tests cover missing/malicious/stale container payloads, fixed Docker command arguments and secret-free output via a mocked Docker subprocess. They do not claim a real daemon or Hakari host was contacted. Actual host collection, permissions, scheduler and read-only mount acceptance remain pending deployment.
